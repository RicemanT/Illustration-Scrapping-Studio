# Dataset planner

The planner chooses which posts to download for a large artist dataset. It works from post metadata (tags, favorites, scores, sizes and dates), so you can plan thousands of artists without downloading images first. Open it from **Dataset planner** in the sidebar.

Planner data is stored in `<library>/planner/planner.db`. It is separate from your collections: running the planner never creates, changes or deletes folders, images or sidecars.

## 1. Inputs

- **artists.csv** — one row per artist with `site` (`danbooru`, `gelbooru` or `e621`), `display_name` and `query_tag` (the exact site tag). `tag_id` and `post_count` are optional. Uploading a new list updates existing artists and disables artists that are no longer listed. Disabled artists keep their harvested data and are re-enabled if they return.
- **characters.csv** — character targets in priority order, with `site` and `tag`. Danbooru and Gelbooru share one character list because they use the same tag names; e621 has its own.

Both files can be generated by `build_master_artists.py` and `build_character_targets.py` in the artist list project.

## 2. Harvest metadata

The harvest pages through each enabled artist's posts, newest first, up to the per-artist limit (default 2,000). Each site runs at its normal one-request-per-second pace, and the three sites run in parallel. Expect roughly one request per 200 Danbooru posts, 320 e621 posts or 100 Gelbooru posts; about 10,000 artists take several hours.

Progress is saved after every page. **Stop harvest**, closing the browser, or restarting the backend never loses finished work: **Start / resume harvest** continues from each artist's saved position and retries artists that failed. **Refresh finished artists** harvests everything again to pick up new posts.

Gelbooru needs its User ID and API key in Settings. Some posts have no downloadable file for anonymous API users; they are skipped as `no file`.

## 3. Plan

**Run plan** selects images for every enabled artist and keeps the result as a numbered run. The steps are:

1. **Skip unusable posts:** animations, images below the minimum short side (default 768 px), extreme aspect ratios, blocked tags (comics, AI-generated, low-res and others; editable), posts credited to several artists, and optionally ratings or years you exclude.
2. **Drop small artists:** artists with fewer usable images than the minimum (default 20) are dropped. Parent/child variants count once.
3. **Pick images in turns.** Every artist picks one image per round, until it reaches the per-artist maximum (default 60). Each pick goes to the image that adds the most:
   - **Quality:** favorites (or score) ranked within the artist, so a small artist's best images rank as highly as a famous artist's.
   - **Novelty:** content the artist's selection does not cover yet. This keeps an artist tag from being tied to one character.
   - **Character need:** the image shows a target character that is still below its target count across all artists.
   - **Rarity:** the artist's images with unusual tags.
   - **Boost:** camera angles and poses on the boost list (for example `from_below` or `foreshortening`).
   No single character may take more than 30% of an artist's images unless the artist has nothing else.
4. **Top up characters:** target characters still below their target (default 30 images) receive extra unselected images from listed artists, at most 10 per artist.
5. **Set repeats:** every artist gets about the same number of training samples per pass (default 200). Artists with fewer images get more repeats, up to the maximum.

The run summary shows kept and dropped artists, image and sample totals, why posts were skipped, and which characters remain below target. Characters that are still short need images from artists outside your list, for example through Character collections.

Settings default to values measured on live Danbooru and e621 data. Heavier character and boost weights replaced too many of an artist's best original works with fan art. Change them under **Score weights and tag lists**; **Load this run's settings** restores an earlier run's configuration.

## 4. Review

Choose a run and an artist to see the selected images and the most popular posts that were not selected. Hover over a thumbnail for its characters, size, rating and score breakdown; click it to open the post on its site.

- **Lock** always includes the image, even if a filter would skip it.
- **Ban** never includes it.
- **Clear** removes your decision.

Locks and bans take effect on the next plan run. Thumbnails are fetched by the backend (Danbooru's CDN rejects direct browser requests) and cached in `<library>/planner/thumbs`.

## 5. Export

**Export manifest** writes `<library>/planner/exports/run-<id>/`:

| File | Contents |
| --- | --- |
| `manifest.jsonl` | One line per selected image: site, post ID, artist tag and name, role (`selected`, `locked` or `character_topup`), repeats, md5, file URL, size, rating, characters, copyrights and score breakdown |
| `selected_<site>_ids.txt` | Selected post IDs for each site |
| `summary.json` | The run's settings and summary |

Downloading the selected posts into collections is not part of the planner yet.

## Memory and storage

Planning keeps every artist's best candidates in memory at once. Ten thousand artists need several gigabytes of RAM, so plan the full list on the Jupyter server; a laptop handles a few hundred artists comfortably. Harvested metadata for about six million posts takes roughly 3–5 GB on disk.
